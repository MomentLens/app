## 4. Build

One package per session, in the card's build order: `/slice S-12 build api`, `/clear`, then `/slice S-12 build mobile`. Load the card as SKILL.md says, `git fetch origin`, and cut `feat/<id>-<package>` from the branch below it: the schema branch for the first package, or the doc-fix branch or `origin/main` when the card gives the slice no schema stage, and the previous package's branch after that. If that branch is not on GitHub, stop and say which stage has not run. Read that package's `AGENTS.md`, the schema files the card names, by path, and the files you will change. Fetch a doc section only if the card lists its id.

**In the mobile build, ask for the screens once.** Before writing any screen, list the screens the card names and ask one question: do they have designs for these, as screenshots or Figma exports, or should you improvise? Never insist, and never ask twice. With no images, build every screen in the style of the screens already in `apps/mobile/src/features/`. With images for some screens, follow those and improvise the rest to match them. An image sets layout and direction; D-112 sets sizes and the spec sets behavior. The ledger records which screens had an image and which were improvised, and the PR's "On a device" section repeats it, so the reviewer knows what to look at.

**The api build owns the card's migration**, if it has one. Create it with `pnpm exec supabase migration new <name>` and push it to the dev project when the tests or the phone need it, following Handbook §13.4 and asking first. Once pushed it is frozen: a change is a new migration.

1. Write each negative test the card lists for this package before the code it tests, run it, and watch it fail. Then write the code and watch it pass.
2. Verify with `node scripts/verify.mjs docs format <package> rls worker-sql --slice <id> --base origin/<the branch below>`. The script saves full logs and prints a table. Complete the negative-test, diff and human-read checks in your tool's `slice-verifier` procedure (`.claude/agents/slice-verifier.md` or `.codex/agents/slice-verifier.toml`) inline. Delegate the pass only when SKILL.md's token gate qualifies it, with the complete changed-file manifest, the slice id, checkout, package, base, invariant numbers and named negative tests. Supply existing logs so the agent reuses completed checks at the same code state. The main agent confirms invariant suspicions and owns the final review.
3. Fix verification failures and rerun the affected checks. After two failed rounds on the same failure, stop, name the cause (missing information, a wrong assumption, the environment, or a flaky test) and ask the user; a third attempt means context is missing (Handbook §18.2).
4. When verification is clean and every required check has evidence, commit this package's work in small conventional commits.

Stay inside the package. Never edit `packages/shared-types`, `docs/` (the done stage writes any `ARCHITECTURE.md` change) or another package; if the work needs one of those, stop and ask. Add a dependency only when the card names it: the read-back asked and the developer approved it there, so add it at the version the card gives without asking again. Ask only when a dependency, its version or its scope differs from the card. When the card is silent, wrong, or conflicts with a numbered invariant, ask the user rather than choosing a reading, and fix the card in the issue, raising its revision, before building on the answer.

If the card says the slice touches the camera, GPS or the upload queue, ask the user to run it on a physical phone and report back, and record what they report in the ledger. To try an API change on the phone before the stack merges, the developer deploys this branch to the dev server (Handbook §13.4); offer the commands, ask before running each, and remind them to put `main` back.

Push the branch and open or update `<id>: <package>` on the stack, as SKILL.md says. Its description names the human-read surfaces verification identified and where each changes in the diff, the negative tests with the verification table, the device check and any shared infrastructure, and links to the issue. Post the ledger entry. Tell the user the next stage: the next package in the card, or `/slice <id> done`.
