## 5. Done

The done stage makes the stack ready for review and records the proof. The order matters: every edit comes before the final verification, and the readiness record comes last, so nothing it records goes stale inside this stage (D-149).

1. `git fetch origin` and check out the top branch of the stack. Load the card as SKILL.md says.
2. **Make the last edits.** If `docs/ARCHITECTURE.md` needs an update, write it now as its own commit on the top branch, citing the D-entry or the merged code, and name it in that PR so the code owners approve it there (D-75, D-107). A code owner's own change needs no other approval. The build stages never edit `docs/`; only this stage and the read-back's doc-fix branch do.
3. **For a code owner's own stack, review it now** (D-117). Run `/code-review` on each PR and fix what it finds on the branch it belongs to; a fix lower in the stack is rebased up as SKILL.md says, with the developer's yes for each force push. Then record it on each PR: `gh pr comment <n> --body "/code-review ran on <reviewed head, short sha> against <base branch>: <n> findings. <What was fixed, in which commit, or why not>."`. An agent tool without `/code-review` reviews each diff against the numbered invariants itself, and says so in that comment.
4. **Check every PR description.** Each names which of the four human-read surfaces it touches, or says none, with where each changes in its diff, and links to the issue. Fix any that does not with `gh pr edit <n> --body-file`. Push every branch you changed.
5. **Verify the head you will record.** Run `node scripts/verify.mjs all --slice <id> --base origin/main` against the whole stack, then complete the verifier procedure's negative-test, diff and human-read checks. Do this inline unless SKILL.md's token gate justifies a delegated pass with the complete changed-file manifest and the existing logs. The main agent confirms its findings; a subagent report never replaces step 3's review. Then read CI on the top PR's head and wait for it to finish: `gh pr checks <top PR> --watch`. A failure sends you back to step 2. A check `scripts/verify.mjs` reported unavailable did not pass; CI's run of it on that head is its evidence, or it is not met.
6. **Answer the explanation again with the evidence.** In the issue body's Explanation section, keep the five questions and replace the plan with what was built: for each answer, the test, CI run, command or device report that shows it holds. Plain words, as the read-back wrote them.
7. **Write the readiness record** in the issue body's Readiness section, the ready-for-review rows, one per item of the Definition of done in `docs/WorkSlices.md`:
   - Result: `met`, `not met`, `n/a: <the reason>`, or `exception: <link to Ukasha's comment in the issue>`.
   - Head: the top branch's head that step 5 verified, `git rev-parse --short HEAD`.
   - Evidence: where a reviewer checks it, such as a test name and file, a CI run, a PR comment or the ledger entry holding the developer's phone report.
   - By: who or what supplied it, such as `verify.mjs`, CI, the developer or Ukasha.

   Leave the ready-to-merge rows to cleanup. Check what you wrote: `node scripts/readiness.mjs --issue <n> --stage review --head <that head>`. Never describe the slice as ready while a row is not met. Only Ukasha grants an exception, by a comment in the issue; ask whether they want to, and never write one yourself.
8. Post this stage's ledger entry, then tell the developer, and stop there:
   1. The stack from bottom to top, each PR with its number and link, and the readiness check's result.
   2. **Review.** GitHub has already requested the code owners' review on every PR. Another developer's review is welcome and never required; if the developer wants one, give `gh pr edit <n> --add-reviewer <their GitHub login>` for each PR and offer to run it. A code owner's own stack has nobody to wait for: step 3 reviewed it.
   3. How it lands: once every PR is approved, or for a code owner reviewed by `/code-review`, and green, and the readiness record is current, it merges from the top down with Rebase and merge (Handbook §12). Folding the stack down drops the bottom PR's approval, so that PR needs approving once more before it reaches `main`. Then `/slice <id> cleanup` in a fresh session, which checks the record and can do the merging too.
